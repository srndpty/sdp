# ADR-0001: 再生エンジンの選定

- **状態**: **Accepted**
- **提案日**: 2026-07-28
- **決定日**: 2026-07-28（P0-A〜P0-D の全検証完了により確定）
- **関連**: [開発計画](../development-plan.md)、[アーキテクチャ](../architecture.md)、
  [P0 技術検証レポート](../p0-report.md)

## 背景

sdp は Windows 11 向けのローカル音声プレイヤーで、通常の再生機能に加えて次を必要とする。

- 0.5〜2.0 倍の再生速度変更
- **ピッチ補正 ON/OFF の切り替え**（ピッチ維持の time-stretch と、速度連動の varispeed の両方）
- リアルタイム周波数スペクトラム表示のための再生 PCM の取得
- WAV / MP3 / OGG Vorbis / OGG Opus / FLAC / M4A(AAC) のデコード
- 個人開発で完遂できる実装量と、exe への同梱が現実的な配布サイズ

ピッチ補正の切替は要件として確定しているため、これを満たせるかどうかが選定の中心になる。

## 検討した選択肢

以下の比較には**未検証の推測が含まれる**。実測は P0 で行い、その結果で本 ADR を更新する。

| 観点 | Qt Multimedia (ffmpeg バックエンド) | mpv (libmpv / python-mpv) | VLC (python-vlc) |
|---|---|---|---|
| 形式対応 | ffmpeg 同梱で広い（U4 で要検証） | ◎ 最も広い | ◎ 広い |
| 速度変更 | `playbackRate`（U2 で要検証） | ◎ `speed`、scaletempo2 で高品質 | ○ 実装はあるが品質は不明（推測） |
| ピッチ補正の切替 | 6.10 のピッチ補正 API（U1 で要検証） | ◎ `audio-pitch-correction` で明示的に切替可能 | △ 実質不可（推測） |
| リアルタイム PCM 取得 | ◎ `QAudioBufferOutput`（U3 で要検証） | ✕ 公開されたタップがない。位置駆動可視化または別デコーダーとの同期が必要 | ✕ 同上 |
| Qt 統合と配布 | ◎ 追加 DLL 不要、PyInstaller の実績あり | ○ libmpv の DLL 同梱が必要（約 40MB） | △ VLC ランタイムの同梱が重い |
| ライセンス | LGPL（PySide6 の配布条件に準拠） | LGPL（libmpv のビルド構成に注意） | LGPL |
| 個人開発での実装量 | 最小 | 中（可視化のために位置駆動設計が必須になる） | 中〜大 |

## 決定

**第一候補として Qt Multimedia（QMediaPlayer + QAudioOutput + QAudioBufferOutput）を採用する。**

### 合格基準（P0 で判定する）

Windows 実機で次をすべて満たした場合に Accepted とする。

1. ピッチ補正関連 API が存在し、ピッチ維持 / ピッチ連動を切り替えられること（U1）
2. varispeed と time-stretch の**双方**が 0.5〜2.0 倍で実用的な音質であること（U2）
3. [開発計画 §4 の P0 検証項目](../development-plan.md#p0-技術検証pr1)に致命的な欠陥がないこと

### 不合格時の扱い

**1 または 2 を満たさない場合は mpv を本命へ昇格させる。**
その際は本 ADR を Superseded とし、`0002-playback-engine-mpv.md` を新規に起こす。
Qt Multimedia を API 仕様の読みだけで不合格にはせず、必ず実機の音響挙動で判定する。

mpv へ昇格する場合の追加決定:

- 可視化は「位置駆動方式」（解析済みファイルの PCM と再生位置から FFT の窓を切り出す）を
  主とし、リアルタイム PCM タップは断念する。
- P4（追従波形）の解析基盤がそのままスペクトラムの供給源になるため、
  実装順は P4 → P5 を維持する（開発計画では最初からこの順にしてあり、切替コストが最小になる）。

VLC は比較のみで**不採用**とする。ピッチ切替と PCM 取得の両面で優位性がなく、配布も重い。

---

## 決定の確定（2026-07-28）

**P0-A〜P0-D のすべてに合格したため、Qt Multimedia の採用を確定し、本 ADR を Accepted とする。**

### Qt Multimedia を採用した理由

1. **必須要件だったピッチ補正 ON/OFF の切替が実際に可能だった。**
   `pitchCompensationAvailability()` が `Available`（`AlwaysOn` でも `Unavailable` でもない）で、
   再生前・再生中・一時停止中のいずれでも設定値が実際に切り替わった。
   これが不可なら mpv へ昇格する予定だったが、その必要がなくなった。
2. **音質が個人利用として許容できた**（人による聴感確認。総合「条件付き合格」）。
3. **リアルタイム PCM をそのまま取得できる。** `QAudioBufferOutput` により、
   別デコーダーとの同期や位置駆動方式のような回り道をせずに可視化を実装できる。
   これは mpv にはない決定的な利点だった。
4. **配布が単純。** 追加のランタイム DLL を自前で用意する必要がなく、
   PyInstaller の標準 PySide6 hook だけで動作する成果物ができた。
5. **個人開発で完遂できる実装量に収まる。**

### P0-A〜P0-D の実測結果の要約

| 区分 | 結果 |
|---|---|
| **P0-A** 基本再生 | 全 12 件合格。主要 6 形式 × ASCII / 日本語・空白パスで、読み込み・duration 取得・位置前進・シーク・EndOfMedia がすべて動作 |
| **P0-B** 速度とピッチ（自動） | `pitchCompensationAvailability` = `Available`。0.5〜2.0 倍（45/33 を含む）の 7 段階 × ピッチ補正 ON/OFF の 14 通りすべてで、再生時間が期待値と 0.5% 以内で一致 |
| **P0-B** 音質（人による聴感確認） | 総合「条件付き合格」。varispeed は全倍率で参照音と一致。time-stretch は 0.75 / 1.5 倍が合格、0.5 倍（軽い残響感）と 2.0 倍（子音の人工感）が条件付き合格 |
| **P0-C** PCM 取得 | 全 8 条件合格。主要 6 形式 + 日本語パスで PCM を取得。440Hz 入力の FFT ピークは 441.4Hz。シーク後は最初のバッファから目的区間の内容（古いバッファの混入 0 件）。4096 点 FFT は 0.02ms で GUI スレッド実行が可能 |
| **P0-D** パッケージ版 | 全 12 条件合格。PyInstaller onedir（161.8MB / 291 ファイル）で、外部 Python・uv・FFmpeg CLI に依存せず動作。日本語・空白を含むパスへ配置しても 22/22 PASS。クリーンビルド 2 回で同一結果 |

### mpv を採用しなかった理由

1. **昇格条件を満たさなかった。** mpv 昇格は「ピッチ補正の切替が不可、または音質が不十分」な
   場合の代替案だったが、いずれも該当しなかった。
2. **リアルタイム PCM を取得できない。** libmpv は音声 PCM のタップを公開していないため、
   可視化は位置駆動方式（解析済みファイルの PCM と再生位置から窓を切り出す）にするか、
   別デコーダーとの同期が必要になる。実装量が明確に増える。
3. **配布が重くなる。** libmpv の DLL（約 40MB）を自前で同梱・更新する必要がある。
4. 個人開発として、利点のない複雑さを増やす理由がない。

VLC は比較のみで不採用（ピッチ切替と PCM 取得の双方で優位性がなく、配布も重い）。

### 判明した制約

採用にあたり受け入れる制約。実装時に必ず考慮する。

1. **`QAudioBufferOutput` は速度・ピッチ処理を適用する前の PCM を返す。**
   `frames/s ÷ sampleRate` が `playbackRate` と一致し、FFT ピークが倍率によらず一定である
   ことで実測確認した。2.0 倍の varispeed 中でも取得 PCM のピークは元の周波数のままになる。
2. **`playbackRate` の読み戻しは float32 精度。**
   0.5 / 1.25 などは往復一致するが、45/33 のような値は相対 1e-8 程度ずれる。
   厳密な等値比較をしてはならず、要求倍率の真値は PlaybackController 側が保持する。
3. **`QMediaFormat` の対応コーデック列挙は実際の再生可否を完全には表さない。**
   `supportedAudioCodecs(Decode)` に Vorbis と Opus が含まれないにもかかわらず、
   実際には両方とも再生できた。可否は実際に読み込んで `errorOccurred` を見て判定する。
4. **`frameCount` は可変。** コーデックごとに異なり（4096 / 4608 / 1152 / 1024 / 960 / 648 など）、
   同一ファイル内でも先頭バッファはプライミングで短い。固定長を前提にしない。
5. **`QAudioBuffer.startTime()` は負値を取り得る。**
   MP3 で -25ms、Opus で -6.5ms を観測した。時間軸計算で負値を弾かない。
6. **`QAudioBuffer.constData()` が `None` を返し得る。**
   バイト列化の前に判定し、想定内の空バッファとして安全にスキップして件数を記録する。
   PySide6 はスロット内の例外を握り潰すため、PcmTap 内で例外を投げない作りにする。
7. **音量とミュートは PCM タップへ反映されない。**
   可視化は音量設定を適用する前の信号を表す。ミュート中でもレベルは振れる。
8. **PcmTap の受信 QObject を GUI スレッドに置く前提ではリングバッファのロックは不要。**
   `audioBufferReceived` が GUI スレッドで受信されることを実測で確認した。
   受信をワーカースレッドへ移す場合はこの前提が崩れ、mutex が必要になる。
9. **曲切替時にはリングバッファを明示的に clear する。**
   実測では前曲 PCM の混入は 0 件だったが、コストがほぼ無く確実なため初期化する。
10. **sampleFormat は Int16 と Float 以外が未観測であり、未対応形式を暗黙変換しない。**
    未観測の `UInt8` / `Int32` は実装せず、受け取った場合は明示的に失敗させる。
    実際に発生した時点で、根拠を記録したうえで追加する。
11. **Python 側の `qInstallMessageHandler` は終了前に解除する。**
    付けたままだと、Python の終了処理後に Qt がログを出した際にアクセス違反で落ちる
    （`QT_DEBUG_PLUGINS=1` で再現・原因特定済み）。

### 将来この決定を再評価する条件

次のいずれかが起きた場合、本 ADR を再検討する（該当時は新しい ADR を起こす）。

- time-stretch の音質が実利用で許容できないと判断された場合
  （0.5 倍・2.0 倍が「条件付き合格」であり、常用して不満が出る可能性が残る）。
- PySide6 / Qt の更新でピッチ補正 API の挙動が退行した場合。
- 対応したい音声形式が Qt Multimedia のバックエンドで扱えないと判明した場合。
- 可視化要件が「実際に聞こえている音」の解析を必須とするまで発展し、
  制約 1 を回避できなくなった場合。
- 長時間再生や実運用で、再生の安定性に問題が見つかった場合。

再評価しても runtime fallback は導入しない。エンジンの変更は本 ADR を Superseded とする
明示的な設計変更として行う（[AGENTS.md](../../AGENTS.md) のフォールバック方針）。

## 結果

- 良い点（実測で確認済み）: 追加ランタイム DLL が不要で配布が単純。`QAudioBufferOutput` により
  リアルタイム可視化が素直に実装できる。Qt のイベントループとの統合も自然で、
  可視化処理を GUI スレッドで回しても CPU 占有は 0.1% 未満。
- 悪い点 / 受け入れた制約: 上記「判明した制約」の 11 項目。
  とくに制約 1（PCM が速度・ピッチ処理前）は可視化の見え方に影響する。
- 差し替えコストの抑制策: UI から再生実装を直接触らせず、
  [`IPlaybackBackend`](../architecture.md#3-主要クラスと責務) に
  差し替えへ必要な最小限のメソッドとシグナルだけを定義する。
  エンジンの変更は runtime fallback ではなく、本 ADR 上の明示的な設計変更として行う。
